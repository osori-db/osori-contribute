# OSORI 기능 개발 오케스트레이터

Next.js 16 + React 19 + TypeScript + Tailwind v4 + Vitest 로 만든 OSORI 기여 도구의 기능 개발을 4인 에이전트 팀으로 수행한다.

**실행 모드: 에이전트 팀** — `ui-builder` 와 `domain-logic` 이 타입 계약을 실시간 합의해야 하고, `integration-qa` 가 모듈 완성 즉시 결함을 되돌려 보내야 하므로 팀 통신이 결과 품질을 좌우한다.

## 팀 구성

| 에이전트 | 소유 범위 | 사용 스킬 |
|---------|----------|----------|
| `feature-planner` | 계획·타입 계약 (`_workspace/01_plan.md`) | — |
| `domain-logic` | `src/lib/**`, `src/app/api/**` | `osori-domain-layer` |
| `ui-builder` | `src/components/**`, `src/hooks/**`, `src/app/*.tsx` | `nextjs-component-patterns` |
| `integration-qa` | `src/**/*.test.*`, 검증 실행 | `frontend-integration-qa` |

모든 `Agent` 호출에 `model: "opus"` 를 명시한다.

## Phase 0: 컨텍스트 확인

작업을 시작하기 전에 `_workspace/` 를 확인하여 실행 모드를 정한다.

| 조건 | 모드 | 행동 |
|------|------|------|
| `_workspace/` 없음 | **초기 실행** | Phase 1부터 전체 진행 |
| 있음 + 사용자가 특정 부분 수정 요청 | **부분 재실행** | 해당 에이전트만 재호출. 계획이 안 바뀌면 Phase 1 건너뜀 |
| 있음 + 새 요구사항 | **새 실행** | `_workspace/` → `_workspace_prev/` 로 이동 후 Phase 1부터 |

부분 재실행 매핑:
- "UI만 / 레이아웃 / 버튼" → `ui-builder` + `integration-qa`
- "검증 / 매핑 / API" → `domain-logic` + `integration-qa`
- "테스트 / 빌드" → `integration-qa`

## Phase 1: 계획 (단독)

`feature-planner` 를 호출한다. 산출물은 `_workspace/01_plan.md` — 요구사항 해석, 영향 파일표, 타입 계약(실제 TypeScript 코드), 작업 분해, 리스크.

계획서에 미확정 질문이 남아 있고 그 답에 따라 산출물이 크게 달라지면, 팀을 만들지 말고 **사용자에게 먼저 묻는다.** 잘못된 전제 위에 4명이 병렬로 쌓아 올린 결과를 되돌리는 비용이 질문 한 번보다 훨씬 크다.

계획을 사용자에게 요약 보고하고 다음 Phase로 넘어간다.

## Phase 2: 병렬 구현 (팀)

`TeamCreate` 로 `domain-logic`, `ui-builder`, `integration-qa` 3인 팀을 만든다. `TaskCreate` 로 `_workspace/01_plan.md` 의 작업 분해를 그대로 작업 목록화하고 의존 관계를 건다.

진행 규칙:

1. **타입 계약이 먼저다.** `domain-logic` 이 타입·시그니처를 확정하고 `ui-builder` 에게 통보한 뒤에 양쪽이 병렬로 진행한다. 계약이 확정되기 전 UI가 앞서 나가면 나중에 전면 수정된다.
2. **소유 범위를 넘지 않는다.** 남의 파일이 바뀌어야 하면 `SendMessage` 로 요청한다. 같은 파일 동시 편집은 변경을 유실시킨다.
3. **점진적 QA.** 각자 모듈을 끝내면 즉시 `integration-qa` 에게 알린다. QA는 전체 완성을 기다리지 않고 그 경계면을 바로 검증한다.
4. **결함은 담당자에게 되돌린다.** QA는 구현 파일을 직접 고치지 않는다.

리더는 작업 상태를 모니터링하되, 팀원의 구현 방식에는 개입하지 않는다.

## Phase 3: 최종 검증 (팀 내 QA)

`integration-qa` 가 전체 게이트를 실행한다.

```bash
npx tsc --noEmit && npm test && npm run build
```

셋 다 통과해야 완료다. 실패 시 담당 에이전트에게 되돌리고 재검증한다 (Phase 3 ↔ Phase 2 루프).

산출물: `_workspace/04_qa_report.md`

## Phase 4: 종합 및 팀 정리

리더가 결과를 종합한다. 팀을 정리하고 사용자에게 보고한다:

- 무엇이 바뀌었는가 (파일별 한 줄)
- 검증 결과 (3개 명령 통과 여부, 테스트 수)
- 계획 대비 빠진 것과 그 이유
- 알려진 제약·후속 과제

## Phase 5: 피드백 수집

작업 완료 후 사용자에게 개선점을 묻는다. 피드백이 오면 유형에 따라 반영한다:

| 피드백 | 수정 대상 |
|--------|----------|
| 결과물 품질 | 해당 에이전트의 스킬 |
| 역할 누락 | 에이전트 정의 추가/수정 |
| 순서·흐름 | 이 오케스트레이터 |
| 트리거 안 걸림 | 스킬 `description` 확장 |

모든 변경은 `CLAUDE.md` 의 변경 이력에 기록한다.

## 데이터 전달 프로토콜

| 방식 | 용도 |
|------|------|
| 태스크 (`TaskCreate`/`TaskUpdate`) | 작업 분배·진행 추적·의존 관계 |
| 메시지 (`SendMessage`) | 계약 통보, 결함 보고, 타 소유 파일 수정 요청 |
| 파일 (`_workspace/`) | 계획서·QA 리포트 등 구조화 산출물 |

파일명 규칙: `{순번}_{에이전트}_{산출물}.md` (예: `01_plan.md`, `04_qa_report.md`)

`_workspace/` 는 사후 검증을 위해 보존한다. `.gitignore` 에 추가되어 있어야 한다.

## 에러 핸들링

| 상황 | 대응 |
|------|------|
| 에이전트 실패 | 1회 재시도. 재실패 시 해당 작업 없이 진행하고 **최종 보고에 누락을 명시** |
| 계약 충돌 (양쪽 주장이 다름) | `feature-planner` 가 중재. 계약서를 갱신하고 양쪽에 재통보 |
| 검증 게이트 실패 | 최대 3회까지 Phase 2 ↔ 3 루프. 3회 초과 시 중단하고 남은 실패를 사용자에게 보고 |
| 요구사항 자체가 모순 | 구현하지 말고 사용자에게 확인 |
| 기존 테스트 회귀 | 테스트를 고쳐서 통과시키지 않는다. 회귀가 의도된 것인지 먼저 판단하고, 의도되지 않았으면 구현을 고친다 |

**테스트를 통과시키기 위해 테스트를 약화하지 않는다.** 이것은 검증 체계 전체를 무의미하게 만든다.

## 테스트 시나리오

**정상 흐름 —** "모달에서 Version을 수정할 수 있게 해줘"
→ Phase 0: `_workspace/` 없음 → 초기 실행
→ Phase 1: planner가 편집 초안 상태 설계, `onSave(row)` 계약 확정
→ Phase 2: domain-logic이 매퍼/검증 입력 경로 정리, ui-builder가 입력 필드+초안 상태 구현, QA가 Props 경계면 즉시 검증
→ Phase 3: tsc/test/build 통과
→ Phase 4: 변경 요약 보고

**에러 흐름 —** QA가 "편집한 값이 매퍼로 전달되지 않음" 발견
→ QA가 `ui-builder` 에게 결함 통보 (위치·증상·원인 포함)
→ `ui-builder` 가 저장 핸들러에 초안 값을 전달하도록 수정
→ QA 재검증 → 통과 → Phase 4

**부분 재실행 —** "버튼 위치만 다시 잡아줘"
→ Phase 0에서 부분 재실행 판정 → `ui-builder` + `integration-qa` 만 호출, Phase 1 건너뜀
